## 真实失败

1. Pro 的 `shop_migration-02` 连续触及输出上限，以 `OutputLimitError` 结束。
   `available` 接口未完成，外部行为断言失败；不是评测口径歧义。
2. Flash-first 的 `shop_migration-01`：Worker 新增迁移测试失败，并出现 Windows
   数据库文件仍被占用的清理错误。运行时按验收失败启动 Pro 修复，Pro 再次输出超限，
   未完成修复。外部业务断言通过，但 unittest 与整体验收失败，因此不能计为成功。

第二项证明失败检测和交接能够触发，没有证明修复成功。原 report 的 repair_rounds
按完成的验证轮次数计算，失败发生在修复过程中时为 0；本摘要另按 handoff 记录计入
**1 次已启动、未完成的修复**，避免误读为从未尝试接手。

两次 8192 输出额度补充实验均成功，支持继续研究模型输出预算的配置，但不能证明
提升额度必然解决超限。它们是新建工作目录的新任务，不是恢复同一个失败会话；
不能拿 2/2 替换原组的失败，也未验证失败现场恢复能力。

## 对“好用”的判断

- Flash 在这些可自动测试的 Python 维护任务中表现稳定，24 个实例均完成，最长
  约 61 秒。适合作为有测试和人工 review 的日常辅助工具。
- Pro 更强的产品定位并不意味着当前配置下一定更可靠。本次 4096 输出预算的
  Pro 和多模型组均为 5/6；多模型没有提高成功率。
- 新增测试是实际执行的一部分，其自身错误和资源泄露也会让任务失败，不能只看
  外部业务断言通过便忽略。测试代码也必须审查。
- 评测共记录 7 次命令拒绝，说明拒绝路径被实际走到，不代表全面安全审计通过。
- 本轮仍不是跨语言/浏览器/生产部署验收；多次重复同一用例不能证明未知需求可靠。

## 后续具体改进

1. 将 Pro 的模型特定输出预算与输入预算联动验证，先用 8192 做更大样本；不要直接
   全局增大默认值或取消额度上限。
2. 改进输出超限恢复：识别反复截断，缩小单步修改，保留失败现场，避免花完额度后
   留下半成品；针对本次两份失败记录做回归。
3. 修复评测的修复尝试统计，分别显示 started/completed/succeeded；保持历史报告不变。
4. 在新增测试中覆盖 SQLite 连接关闭、异常路径与 Windows 文件清理，避免测试资源泄露。
5. 下一批换 TypeScript、前端和真实构建任务，减少对这一套 Python 固定用例的依赖。
