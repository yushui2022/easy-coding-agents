# v0.14：Worker 执行、真实检查、主模型接手

本版提供显式的单任务串行链路，默认不启用：

```text
指定 Worker 完成任务
  → 按顺序运行用户指定的检查
    → 全部通过：结束，不调用主模型修复
    → 普通失败：在显式修复预算内交给当前主模型修复，再重跑整组检查
    → 超时、拒绝、取消、未知结果、Worker 未完成：停止并保留现场
```

## 用法

先按 [v0.13](UPGRADE-v0.13.md) 配置模型档案，并将 `helper` 加入 `[agent].worker_profiles`。保持现有主模型设置，再运行：

```sh
eca -p "修复导出模块，并保持现有接口兼容" --worker-first helper --verify-command "python -B -m pytest tests/test_export.py" --repair-attempts 1 --allow-shell
```

非交互模式如需允许文件编辑，可另加已有的 `--accept-edits`。`--allow-shell` 会授权该次运行的 Shell 能力，不只授权检查命令；按现有权限策略谨慎选择。

- 不指定 `--worker-first`，原有单 API 和主模型工作流保持不变。
- `--worker-first` 必须与 `-p`、检查命令共同使用，只允许非隔离的父会话 code 模式，档案必须已经明确启用。
- 省略 `--repair-attempts` 时预算为 0：Worker 和检查照常运行，检查失败直接停止，不自动增加主模型费用。
- 修复次数沿用已有 0..3 上限；每阶段还受模型轮数限制，Worker 有独立超时。这是次数限制，不是金额预算。
- 可重复指定 `--verify-command`，最多 10 项，首个失败后停止；修复后从第一项重新检查，要求全部结果对应同一源码指纹。

## 接手和记录

Worker 通过现有共享工作目录的 delegate 执行，继续使用正常审批和文件修改日志。本链路不是并行隔离合并：Worker 的修改立即存在于工作目录中，即使失败也保留，不自动回滚。主模型收到原始要求、Worker 的有界报告、子会话 ID 和真实检查输出，并被要求检查现有修改、针对问题修复，不重新执行整项任务。

父会话持久记录 delegate 调用和对应结果，子会话保留完整操作历史。`verification_suite.worker` 保存 Worker 身份和状态，`handoff` 保存修复模型、次数与触发原因；`/progress` 和 JSONL 的 verification_suite 事件可以查看。父子模型继续使用同一任务的用量账本。

取消会留下 interrupted 状态并修复工具调用配对。恢复会话不会自动重放 Worker 或检查命令；检查中断时保留已经完成的轮次。通过后源文件发生变化会显示 stale。

## 验证与边界

新增端到端测试使用模拟模型与真实 Shell 检查：Worker 写错内容 → 真实断言失败 → 主模型修改已有文件 → 真实断言通过。同时检查工具消息配对、两种模型的费用归集、成功时不调用主模型、预算为零、拒绝/超时不接手、Worker 故障、取消恢复和参数校验。

检查通过只证明所选命令通过，不保证需求覆盖充分；Worker 的自然语言报告也不是验收依据。没有实现动态智能路由、任意 Worker 故障自动重试或蜂群递归调度。没有下载本地模型或调用付费 API。
