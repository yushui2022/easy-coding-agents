# ECA Desktop 0.25.0 工作台升级

## 目标与审计

参考用户提供的《从 Demo 到企业级质感：前端升级执行指南》与产品设计方法论文档，以“选择项目 → 发起任务 → 看清过程 → 决定授权 → 检查结果 → 继续会话”为主链路。保留 Electron、React、共享 Python 核心、中文界面和 ECA 橙色标识。

原界面的主要问题：

1. 输入更新触发整段历史重新渲染；流式文本反复解析 Markdown，展开前也挂载完整工具日志。
2. 轻量状态仍携带不断增长的全文；完整刷新重复传送大日志，数据量随会话增加。
3. 工具调用和返回分成原始 JSON 卡片，用户难以迅速看出执行对象、状态和结果。
4. 授权和阶段进度混在滚动对话里；验证配置展开后占用阅读空间，结果记录挤在修改列表下方。
5. 会话缺少搜索和折叠导航，标题层级与长记录浏览不足。

## 文件与实施顺序

- `eca/desktop_rpc.py`：兼容的预览、单条完整记录、增量输出、后端及流标识；先验证通信语义。
- `desktop/src/main/index.ts`：合并高频输出通知；保持立即处理结构事件和取消通道。
- `desktop/src/renderer/Transcript.tsx`：记忆化历史、配对工具摘要、按需展开、完整记录读取及失效检查。
- `desktop/src/renderer/index.tsx`：会话导航、固定授权、验证页、分段历史与最新位置入口；避免迟到请求串会话。
- `style.css` / `workbench.css`：明确导航/阅读/结果栏的密度，保留深浅主题、焦点与窄窗口详情弹窗。
- 真实隐藏 Electron 验收和性能基准 → Python/CLI 回归 → Windows 打包 → 同口径打包复测。

## 产品行为

左侧负责项目与会话，中间只承担任务对话和操作决策，右侧按修改、验证、进度、用量分开。工具行默认呈现执行对象和结果摘要，原始参数和输出点击后读取。验证配置在提交时收起，配置值保留；审批固定在输入区上方，拒绝与停止仍是两个不同操作。

输入期间保留已完成历史组件；流式阶段显示纯文本，完成后再渲染 Markdown。历史最多同时展示 200 条（最近 50 条与已加载 150 条），中间收起的记录明确显示数量。此限制只控制显示，不截断模型任务、原始会话或工具结果。

## 验证与真实风险

性能测试使用 240 条合成消息、每条工具结果约 48K 字符、本地流式模型和独立 G 盘目录。不使用用户凭据、不控制用户窗口。输入指标从 DOM input 捕获事件到 React 离散事件提交后的微任务，排除隐藏窗口定时器/绘制节流；不能等同物理显示的输入到像素延迟。停止指标使用点击派发后的 MutationObserver，另记录即时反馈和清理完成。

旧版隐藏窗口 rAF/定时器得到的约 1 秒值已判定不适合作为输入延迟证据，不作为优化幅度。新的基线与升级版必须使用相同方法和打包程序。模型思考、服务端生成和网络延迟没有因界面改版而消失。

风险包括超长单条最终 Markdown 的解析、外部服务延迟、工作区指纹检查成本，以及缺少独立干净 Windows 验收环境。分段显示与摘要不是验证结果；通过仍仅代表实际执行的所选命令。不会把本机打包测试当成所有设备的稳定性保证。

最终测试数据与安装状态见 `VERIFICATION-0.25.0.md`。
